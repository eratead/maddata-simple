## 1. AI Campaign Assistant — production stabilisation

### What was wrong (in the order it was found)

1. **Frontend role label `'ai'` instead of `'assistant'`** in
   `resources/views/campaigns/edit.blade.php` — backend validation requires
   `role:user|assistant`. First chat turn worked, every subsequent turn 422'd
   with the generic "Something went wrong" toast.
2. **Cloudflare 403** on calls to `api.anthropic.com`. Default `GuzzleHttp/X`
   User-Agent scored badly on Cloudflare's bot model and intermittently got the
   "Just a moment..." JS challenge back as a 403. Confirmed by capturing the
   response body in the `ai` log channel — body started with
   `<!DOCTYPE html>...<title>Just a moment...</title>` plus
   `script-src https://challenges.cloudflare.com`.
3. **Truncated JSON** when the response hit `max_tokens: 1024`. Long Hebrew
   briefs (~600 chars input + audience list) generated 1,461-char replies that
   were exactly at the cap and cut mid-JSON. `stop_reason` log field added to
   diagnose; raised the cap to **2048**.
4. **15s `Http::timeout`** was too tight for big briefs. Raised to **60s**.
   Nginx default `fastcgi_read_timeout` is 60s, so we stay within it.
5. **Prose-wrapped JSON** — for complex briefs the model emits chain-of-thought
   markdown ("I need to map this brief carefully:\n\n**Demographics:**...")
   *before* the JSON object, despite the system prompt forbidding it. Parser
   now tries direct decode first, then falls back to extracting the outermost
   `{...}` block.

### Logging upgrades

- Upstream errors now capture a 500-char `body_excerpt` in
  `assistant.upstream_error`.
- `assistant.parse_failure` now also logs `stop_reason`, `raw_text_head` (first
  300 chars), and `raw_text_tail` (last 300 chars).
- `assistant.response` now logs `input_tokens`, `output_tokens`,
  `cache_creation_tokens`, `cache_read_tokens` from `usage`. Per-request token
  cost is now visible in production logs without going to the Anthropic
  dashboard.

### Prompt caching (1-hour TTL)

The audience list embedded in the system prompt is ~7-8K tokens and almost
never changes. Split the system prompt into two content blocks:

- `[0]` cacheable: instructions + AVAILABLE AUDIENCES + UPDATABLE FIELDS +
  JSON rules. Marked `cache_control: ['type' => 'ephemeral', 'ttl' => '1h']`.
- `[1]` dynamic: CURRENT FORM STATE + today's date.

Required the `anthropic-beta: extended-cache-ttl-2025-04-11` header.
Production verification: first call wrote 8,920 tokens to cache
(`cache_creation_tokens: 8920`), second call read them back
(`cache_read_tokens: 8920`). Per-call cost dropped from ~$0.029 to ~$0.011 on
cached reads. Active editor sessions ≈ -50% cost.

## 2. Activity digest emails — moved from in-request trigger to a 2h scheduler

### What changed

`ActivityLogger::log()` used to call `checkAndSendDigest()` on every CRUD
write — every write paid a cache lookup, and digest cadence depended on
traffic (no traffic = no digest). Replaced with a dedicated artisan command:

- **`App\Console\Commands\SendActivityDigest`** (`php artisan
  digest:send-activity`) — reads `last_activity_digest_sent_at` from cache,
  finds new logs since that timestamp, queues `ActivityDigestMail` to active
  opted-in users, always advances the timestamp.
- Registered in `routes/console.php` with `Schedule::command('digest:send-
  activity')->everyTwoHours()` — runs at minute 0 of every even hour.
- `ActivityLogger` is now just a logger again. The `checkAndSendDigest()`
  method and all related imports are gone.
- 6 new Pest tests in `tests/Feature/Commands/SendActivityDigestTest.php`
  covering the happy path, no-activity path, opt-in / inactive filter, window
  correctness, timestamp advancement, and a regression confirming
  `ActivityLogger::log()` no longer enqueues mail as a side effect.

**Deployed to production** 2026-05-04 (commit `aed6f2c`). User confirmed the
17:00 digest mail arrived; cron entry visible in `php artisan schedule:list`.
Next runs: 19:00, 21:00, 23:00, etc. — only mail when there's activity in the

## 3. Google SSO + TOTP hybrid authentication

### Final design (as shipped to staging)

Every login starts with **email + password**. Google is offered as an
alternative second factor — never as a standalone login button. There is no
role-based TOTP requirement. The single invariant is: a user must always
have at least one second factor (TOTP or Google).

| Per-user state | `2fa.challenge` shows |
|---|---|
| `google2fa_secret` set, no Google | TOTP code input only |
| `google_sub` set, no TOTP | **server-side auto-redirect to Google** (no click) |
| Both set | TOTP input + "Or verify with Google" button |
| Neither | Redirected to `2fa.setup` (forced enrollment) |

`2fa.setup` is a two-card picker: Google card (top, recommended) + TOTP card
(below, body collapsed by default, expands on click).

### Architectural choices worth remembering

- **Linking key is the Google `sub`, not the email.** A user's MadData email
  never has to match the Google account email. This means a user can have a
  MadData email like `gurovm@gmail.com` and connect any Google account,
  including one with a different email.
- **No anonymous "Sign in with Google" entry point.** That was in an earlier
  iteration of the spec; user feedback rejected it because clicking the button
  with an unlinked Google account produced a confusing error. Removed
  entirely.
- **No role-based TOTP gating.** Was in an earlier iteration. User asked to
  drop it ("does not harm security significantly"). All users pick their own
  second factor.
- **Lockout invariant** is the only safety guard:
  - Disable TOTP requires Google linked.
  - Disconnect Google requires TOTP enrolled.
  - Server-enforced (422 on violation) and UI-enforced (greyed button +
    tooltip).
- **`session('login_method')` flag was added then removed.** With Google as a
  pure 2FA option (not a separate login method), the single `2fa_verified`
  flag is enough.
- **Auto-verify for SSO-only users.** When `showChallenge()` runs and the user
  has only Google linked, controller skips the view and does
  `Socialite::driver('google')->redirect()` directly. Loop protection: any
  failure path in `doVerify()` sets `block_google_auto_verify` in session,
  consumed one-shot by `showChallenge()` so the user can pick a different
  Google account or sign out without looping.
- **Existing TOTP users cannot add Google at the challenge screen** — they
  must verify with TOTP first, then link via Settings → Sign-in methods.
  Reason: at challenge time only the password has been verified. If we let a
  password-only request bind a *new* Google identity to the account, we'd be
  defeating the TOTP that was supposed to defend against password compromise.
  At setup time there's no factor to defend yet, so the asymmetry is
  load-bearing.
- **Discoverability hint** added on `2fa.challenge` for TOTP-only users — a
  small grey box pointing to Settings → Sign-in methods so users learn the
  option exists without having to dig.

### Bugs found and fixed during staging walkthroughs

1. **Nested `<form>` elements** in three Settings-page modals (Connect /
   Disconnect Google / Disable TOTP) — outer Alpine wrapper was
   `<form @submit.prevent>`, inner real form was nested. Browsers silently
   drop nested forms. Outer turned into `<div>`.
2. **Settings page layout** didn't match `profile/edit.blade.php` — had a
   centered `max-w-2xl` wrapper and a duplicate `<x-page-header>`. Aligned to
   the existing pattern.
3. **Socialite state mismatch** in all three OAuth flows. Passing custom state
   via `Socialite::driver('google')->with(['state' => ...])` didn't override
   what Socialite stored in the session for CSRF validation, so on callback
   `Socialite::driver('google')->user()` threw `InvalidStateException`. Fix:
   drop the state-override entirely; carry intent in two session keys
   (`google_oauth_intent` and `google_oauth_user`) consumed by the callback.
   Socialite's CSRF protection now works as designed.
4. **`auth.google.callback` was not in the `RequireTwoFactor` exempt list.**
   When Google redirected back, the middleware fired *before* the callback
   controller could run the link/verify, saw "no factor enrolled" (because
   the link was about to happen but hadn't), and redirected to `/2fa/setup`.
   The session intent + user keys stayed in the session because the
   controller never `pull`'d them, so retrying produced an infinite loop.
   Fix: added `auth.google.*` to the exempt list.
5. **Logout link broken on `/2fa/challenge`** — same nested-form bug as #1.
   Hidden `<form id="logout-form">` was nested inside the verify form,
   browser dropped it, `getElementById` returned null. Fix: single shared
   logout form moved outside the verify form, sibling to the wrapping `<div>`.
