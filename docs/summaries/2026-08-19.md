## 1. What was built

A **System Health Monitor** — a checks/status vertical, ported down from the erate-v2 fleet monitor and scaled to MadData's single droplet. Deliberately reuses erate-v2's names and contracts (`HealthStatus`, `HealthCheckResult`, `HealthSnapshot`, `SystemHealthService`, `HealthMarkers`) so one operator carries one mental model across both projects.

- **Phase 1** — 26 checks across host / edge / app / workers / data / backups, plus `php artisan health:check` (failing-first table or `--json`, exit code driven by `--fail-on`).
- **Phase 2** — `health:alert`, scheduled every 5 minutes: transition-based email, nothing fires on a single observation, persisting problems nag every `HEALTH_REALERT_HOURS`, recovery always notifies.
- **Phase 3** (admin page + header pill) and **Phase 4** (dependency/version checks `d1`–`d4`) are **not built**.

Spec: `docs/specs/system-health-monitor.md` · Runbook: `docs/runbooks/health-monitor.md` · Map: `docs/architecture_map.md` §18 · Tasks: `docs/tasks/todo.md` (HM-*)

**The structural idea:** a root OS cron writes host facts to JSON on tmpfs; the app only ever reads it. PHP-FPM never shells out, never holds sudo, never talks to systemd or apt. Because that path contains no Redis, MySQL or Laravel, it still reports correctly when those are exactly what is broken.

## 3. Bugs that only a real box could find

Five defects were invisible to tests and code review, and surfaced solely by deploying and watching:

1. **CPU read a steady 100% on a 98%-idle box.** Production is **single-core**; the facts cron sampled one second at `:00`, exactly when `schedule:run` boots PHP. The check was measuring its own overhead. Health tasks now run in-process (`Schedule::call` + `Artisan::call`, not `Schedule::command`, which spawns a PHP process per task); CPU averages over 15s; cron offset by `sleep 25`.
2. **B2 reported "the dump shrank to 47% of median"** because the facts cron stats the backup directory mid-write. Would have been a false alarm every night at 03:00.
3. **The TLS cert lives at `new.ad.maddata.media/`**, not `ad.maddata.media/` — a droplet-migration leftover. P2 would have been STALE forever, silently.
4. **A reboot wiped the backup marker** (it sat on tmpfs beside the facts file). Facts are a live *sample* and should die with a reboot; the marker is a *record* and must not. Now at `/var/backups/maddata/backup-last.json`.
5. **A reboot looked exactly like an outage** and sent a real false alarm. Consecutive-observation suppression could not help: the box was already in a DEGRADED episode, and escalations inside an episode alert immediately by design. H1 and `health:alert` now read `/proc/uptime` and hold for `HEALTH_BOOT_GRACE_SECONDS` (180).

**And the one the audit caught:** the monitor gave **different answers to different users**. The backup marker sat inside a `700 root:root` directory, so `www-data` — the UID that runs the scheduler, PHP-FPM and the alerter — read `CRIT "marker missing"` while every check run as root read green. It fired a false alert. See §5.

## 6. Standing rules learned today

Both recorded in `docs/lessons.md`:

- **PHP runtime upgrades are feature-sized work.** Staged first, full suite run *on the new runtime*, never bundled into another request, and both `php8.4-fpm` and the queue worker restarted. Check `php -m` before/after — a missing extension breaks Laravel more often than a language change. And confirm staging can actually run the tests before trusting it: staging lacked `pdo_sqlite`, which turns "validated" into theatre.
- **Verify as the UID that runs the code, not as root.** Root ignores permission bits. An entire day's "25/26 green" was measured as root while `www-data` saw an OUTAGE.
- **`apt-check`'s security count is not actionable on its own** — resolve it to actual installed packages first.
