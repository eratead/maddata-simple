## 3. Three corrections that came from production, not from tests

Worth reading before touching this vertical again.

1. **`d2` took three attempts.** Shipped → two permanent CRITs. Fixed by testing the version string for a distro marker → worked for MySQL, *structurally impossible* for Redis, which self-reports a bare `7.0.15`. Fixed properly by having the facts script publish dpkg package versions. **A check that distinguishes two states must be able to reach both**; a test whose answer is structurally fixed reads like a finding. In `docs/lessons.md`.
2. **`cache:clear` was erasing the monitor's memory.** Markers shared the app cache store, so every deploy wiped them and healthy jobs reported "has never completed". Same class as the tmpfs backup marker a reboot ate. Markers now live in a dedicated `health` **file** store, which also removes their dependency on MySQL and Redis — two of the things being monitored.
3. **`npm run build` is not optional** when a change touches `resources/`. `/public/build` is gitignored, so new Tailwind classes simply do not exist on a server that only pulled and ran composer. The page renders, unstyled, and nothing errors. In `docs/lessons.md`.

## 4. The tri-audit

Three agents over `a6ba5eb..f6a9ff3`; every finding verified before acceptance, five rejected on the evidence. Disposition: `docs/audits/health-monitor-phases-3-4-2026-08-19-SUMMARY.md`.

**The headline was one design mistake with three faces.** Routing `platform` to the digest correctly silenced advisories — and incidentally silenced:

- **A crashed check class**, which the catch-all tags `platform`. Worse: because a crashed check's results vanish from the snapshot, an open episode could drop to all-clear and email **"Everything recovered"** for a problem still failing.
- **`X2`**, the only check that sees an attack in progress.
- **The header pill**, which read amber permanently from two never-clearable WARNs, so no new warning could ever change it.

Fourteen fixes applied in `a8dd6fc` + `6964bf1`, including: the polled endpoint no longer rebuilds (it was doing a full inline rebuild with outbound HTTPS whenever the marker store was unreadable); `OsPatchCheck` no longer reports OK for a 30-day backlog it cannot measure; the stale badge no longer depends on the browser's clock; `d4` no longer warns on every routine `composer require`.

Then, in rough priority:

2. **The `d1` dependency upgrade.** Its own branch: `phpspreadsheet` crosses a major version, exports are user-facing, and it also unblocks the suite's memory ceiling. Finish with `deps:mark-patch-run`, which is deliberately still "never recorded".
3. **`CACHE_LIMITER=redis` on production.** The rate limiter resolves to MySQL — ~8 round trips per poll, ~23,000/day per open monitor tab, against an endpoint issuing none of its own. The config key exists; it is unset by default because staging has no phpredis.
4. **Root cron runs `health-facts.sh` from the www-data-owned deploy tree** — www-data code execution becomes root in 60s. **Verify the actual ownership first**; if the tree is root-owned this is Low, not High.
5. **`distroPackaged()` matches Oracle's own `-1ubuntu22.04` builds**, so the spec's escalation guarantee does not hold. The honest evidence is archive origin (`apt-cache policy`). Recorded, not fixed — the spec's overclaim is corrected in §10.
6. `config:cache` + `view:cache` in the deploy recipe; document the `sleep 25` vs worst-case `schedule:run` invariant (Phase 4 cut its margin from ~24s to ~11s); `unattended-upgrades`, security pocket only.
